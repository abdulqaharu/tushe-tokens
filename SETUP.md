# Setting up @tushe-abdulqahar/tokens: a complete walkthrough

This assumes zero prior context. Follow it in order. Steps marked **(one-time)** you never repeat. Steps marked **(every time)** are your real ongoing workflow.

Part 0 below is new: a map of every file in this repo, what makes it, and what it feeds. Read that first, it explains *why* the later steps exist rather than just *what* to click.

---

## Part 0: The files, and how they feed each other

| File | Where it comes from | What it feeds |
|---|---|---|
| `src/tokens.json` | Exported by the Tushe Token Export Figma plugin (a manual click, not a command) | `scripts/build.js` reads this and nothing else as its source |
| `scripts/build.js` | Written once, lives in this repo | Reads `src/tokens.json`, writes everything in `dist/` |
| `dist/tokens.css` | Generated by `build.js` | Every token as a plain CSS custom property. What `@import` loads for switching `data-theme`/`data-neutral`/`data-accent`/`data-radius`/`data-font` |
| `dist/theme-map.css` | Generated by `build.js` | Bridges clean structural tokens (spacing, radius, font size/family/weight/tracking/leading) into Tailwind's `@theme inline`. Only categories with a confirmed real Tailwind v4 namespace are included, border-width/opacity/skew are deliberately left out rather than guessed |
| `dist/utilities.css` | Generated by `build.js` | Hand-authored `@utility` classes (`bg-brand-bold`, `text-surface-bold`, `icon-surface-subtle`, `border-*`, plus `ring-*`/`outline-*` from focus-ring tokens) for role-aware semantic color, the ones that would collide if left to Tailwind's automatic color bucket. There's no `duration` or `easing` category, because Tushe's actual Figma file doesn't have those primitives, this file reflects real data, not a copied template |
| `dist/text-styles.css` | Generated by `build.js` | Compound `text-*` classes (`text-body-base-normal`) from Figma's 75 text styles, bundling font-size/line-height/letter-spacing/weight into one class. Mobile-first: mobile values are the default, overridden at 768px+ where web differs. Font-family excluded on purpose, pair with `font-sans` (already inherited from the root layout) or `font-mono` for `text-code-*` |
| `package.json` | Written once | Tells npm what to publish (`dist/`), how (`publishConfig`), and where the repo lives |
| `.github/workflows/publish-tokens.yml` | Written once | Watches `src/tokens.json` specifically. When it changes, runs `build.js`, bumps the version, commits, and publishes |

The practical upshot: **all four `dist/` files are real now.** A project that installs this package gets CSS variables (`tokens.css`) and, if it's on Tailwind v4, the `@theme`/`@utility` bridges too (`theme-map.css`, `utilities.css`, `text-styles.css`).

## Part 1: Get the files into a real GitHub repo

**(one-time)**

1. Go to github.com, click **New repository**. Name it `tushe-tokens`. Leave it empty. Create it.

2. Open a terminal in the `tushe-tokens-package` folder (the one containing `package.json`, `scripts/`, `src/`, `dist/`, `.github/`).

3. Turn it into a git repo pointed at the one you just made:
   ```sh
   git init
   git add .
   git commit -m "initial commit"
   git branch -M main
   git remote add origin https://github.com/YOUR-GITHUB-USERNAME/tushe-tokens.git
   git push -u origin main
   ```

4. Fix the placeholder in `package.json`:
   ```json
   "url": "git+https://github.com/<org-or-user>/tushe-tokens.git"
   ```
   Replace `<org-or-user>` with your real username or org, then:
   ```sh
   git add package.json
   git commit -m "fix repo url"
   git push
   ```

5. `package.json` says `"license": "MIT"`. That's a real choice, not a placeholder, MIT means anyone can use this package, including outside Tushe. Confirm that's actually what you want before moving on.

## Part 2: Create the npm account and claim the package name

**(one-time)**

6. Sign up at npmjs.com if you don't have an account.

7. Turn on two-factor authentication now. npm requires it for publishing, no way around it, better to do it before you're mid-setup and blocked.

8. Claim the `@tushe` scope: profile → **Add Organization** → name it `tushe`. Free tier orgs can publish public packages at no cost.

9. Publish once, manually, from your machine, this is what makes the package exist so npm has something to attach automation to:
   ```sh
   npm login
   npm publish
   ```
   `publishConfig.access: "public"` is already set in `package.json`, so this goes public on the first try.

10. Confirm: npmjs.com/package/@tushe-abdulqahar/tokens should be live.

## Part 3: Configure Trusted Publishing

**(one-time)**

This is what lets GitHub publish new versions with no stored password anywhere.

11. On your package's npmjs.com page → **Settings** → **Trusted Publisher** → choose **GitHub Actions**. Fill in:
    - Organization or user: your GitHub username/org
    - Repository: `tushe-tokens`
    - Workflow filename: `publish-tokens.yml` (exact match, this is the most common typo-driven failure later)
    - Leave environment blank

12. **This matters specifically because of npm's current defaults**: as of September 3, 2026, new Trusted Publisher configurations default to staged-only publishing, a human has to approve each release with 2FA. This repo's workflow is written to publish directly and automatically, so you need to explicitly enable **direct publish (`npm publish`)** during this setup, not leave the default as-is.

13. Save.

14. On GitHub: repo → **Settings** → **Actions** → **General** → **Workflow permissions** → **Read and write permissions**. Save. (Separate from npm's permission, this is what lets the workflow push its own version-bump commit back to your repo.)

## Part 4: Your ongoing workflow

**(every time you update the design system)**

15. Run the Figma plugin, download the new `tokens.json`.

16. Replace it and push:
    ```sh
    cp ~/Downloads/tokens.json src/tokens.json
    git add src/tokens.json
    git commit -m "update tokens"
    git push
    ```

17. That's the entire manual step. GitHub Actions rebuilds `dist/`, bumps the version, commits, and publishes, automatically, every time.

18. Watch it: **Actions** tab, a run starts within seconds of your push.

19. Confirm: npmjs.com/package/@tushe-abdulqahar/tokens shows the new version number.

## Part 5: Using it in a consuming project

**(one-time per project)**

20. Install, no auth needed, it's genuinely public:
    ```sh
    npm install @tushe-abdulqahar/tokens
    ```

21. If you're not using Tailwind, just import the raw variables:
    ```css
    @import "@tushe-abdulqahar/tokens/tokens.css";
    ```
    Every token is a `var(--...)`. Switching `data-theme`, `data-neutral`, `data-accent`, `data-radius`, or `data-font` on `<html>` already works, live.

22. If you're on Tailwind v4, import all four, in this order, each of the last three references variables the one(s) before it define:
    ```css
    @import "@tushe-abdulqahar/tokens/tokens.css";
    @import "@tushe-abdulqahar/tokens/theme-map.css";
    @import "@tushe-abdulqahar/tokens/utilities.css";
    @import "@tushe-abdulqahar/tokens/text-styles.css";
    ```
    Tailwind's own build (`next dev` / `next build`, nothing extra to run) compiles the `@theme` and `@utility` rules into real classes. `class="bg-brand-bold"` and `class="icon-surface-subtle"` work directly, no extra config.

## Part 5b: Font setup for non-Next.js projects (Vite, plain React, etc.)

**(one-time per project)**

Steps 20–22 work identically regardless of framework, **except for font family switching specifically**. Everything else, `data-theme`, `data-neutral`, `data-accent`, `data-radius`, every color and spacing token, is plain CSS and doesn't care what rendered the page.

Font family is the one exception, and it's worth understanding why before just copying the snippet below. `tokens.css` never defines what `--font-preset-1` through `--font-preset-5` actually *are*, it only references them (`var(--font-preset-1)`, etc.). In a Next.js project, `next/font/google`'s `variable` option is what defines those five variables, by generating a scoped class in the root layout. Vite and plain React have no equivalent of that API, so without extra setup, those five variables are simply never defined, and font text silently falls back to the browser default, no error, just wrong-looking text.

The fix is to define those five variables yourself, once, via a plain Google Fonts `<link>`:

23. In `index.html`, inside `<head>`, before your app's own stylesheet:
    ```html
    <link rel="preconnect" href="https://fonts.googleapis.com">
    <link rel="preconnect" href="https://fonts.gstatic.com" crossorigin>
    <link href="https://fonts.googleapis.com/css2?family=Google+Sans+Flex:wght@400;500;600;700&family=DM+Sans:wght@400;500;600;700&family=Outfit:wght@400;500;600;700&family=Manrope:wght@400;500;600;700&family=Inter:wght@400;500;600;700&display=swap" rel="stylesheet">
    ```
    The two `preconnect` links go first, letting the browser warm up the connection to Google's servers in parallel with the rest of `<head>`, rather than only starting once the actual stylesheet request fires.

24. In your global CSS, before importing the token package's files, define the five variables using the *real* font names directly (unlike `next/font`, a plain `<link>`-loaded font registers its real name globally, so there's no synthetic scoped name to reference):
    ```css
    :root {
      --font-preset-1: "Google Sans Flex", sans-serif;
      --font-preset-2: "DM Sans", sans-serif;
      --font-preset-3: "Outfit", sans-serif;
      --font-preset-4: "Manrope", sans-serif;
      --font-preset-5: "Inter", sans-serif;
    }
    ```

25. Nothing else changes. `data-font="preset-1"` still does exactly what it does in the Next.js setup, it just resolves against this plain `:root` block instead of a `next/font`-generated class.

Two things worth knowing, not just copying blind:

- **Google Sans Flex is a genuinely recent addition to the public Google Fonts CDN** (November 2025, when Google open-sourced it), and it's a variable font with several axes beyond weight (grade, slant, width, roundness). The `:wght@` syntax above pulls only the weight axis at the four values the system actually uses. If the design ever wants to use its other axes deliberately, the URL construction would need to change.
- Font family names in these URLs have to match Google's exact naming, spacing and capitalization included, or the request silently 404s for just that one family while the other four keep working. Worth a quick check against the font's specimen page on fonts.google.com if something looks like it's not loading.

## If something goes wrong

- **`npm publish` in step 9 fails**: unfinished 2FA, or the `@tushe` scope isn't actually yours yet.
- **The Action fails on publish with a 404**: the workflow filename in your Trusted Publisher config doesn't exactly match `publish-tokens.yml`.
- **The Action succeeds but npmjs.com doesn't show a new version**: check for a staged, unapproved version, step 12 was likely skipped.
- **The Action doesn't run at all**: your change didn't touch `src/tokens.json` specifically.
- **`bg-brand-bold` doesn't work in your project**: check import order first, `theme-map.css` and `utilities.css` need `tokens.css` imported before them, and confirm your project is actually on Tailwind v4 (`@utility` is a v4-only directive).
- **Fonts look wrong in a Vite/React project specifically, but everything else themes correctly**: this is almost always the font gap described in Part 5b, `next/font`'s job was never replaced. Check that the `--font-preset-*` variables are actually defined somewhere your app loads.
